# ICS Calendar Builder and Validator

Calendar .ics validator and builder. Paste an .ics file and see RFC 5545 findings grouped MUST, SHOULD and note, or build an event file folded correctly at 75 octets. Single file, offline.
RRULE is a recurrence rule, not a cron expression, so if you came here for cron syntax you want [cron-next-runs-builder](https://github.com/0xelitesystem/cron-next-runs-builder) or [cron-plain-english-reader](https://github.com/0xelitesystem/cron-plain-english-reader) instead. Those two read a different grammar and this page does not touch it.

**Live demo:** https://0xelitesystem.github.io/ics-calendar-builder-and-validator/

## Use

Two modes on one page.

**Validate.** Upload an `.ics` file or paste `.ics` text. The page reports a verdict line and three separately counted groups: MUST findings, SHOULD findings, and notes. Every finding names the check, where it sits (a physical or logical line number, a byte offset, or the whole file for something missing or file-wide), and the verbatim normative text from RFC 5545 that the check comes from, with its section number.

The two input paths are not equivalent, and the page says so on screen. Uploading a file gives the page the raw octets, so every byte-level check is exact. Pasting does not: a textarea normalises every CRLF to a bare LF before script can read it, so the CRLF check has nothing left to measure, and a fold landing inside a multi-octet sequence has already become U+FFFD and is unrecoverable. On the paste path the bare-LF check is switched off rather than guessed at, and a persistent notice says which checks are weakened.

The checks, all read off the published grammar:

| Tier | Checks | What they cover |
|---|---|---|
| MUST | 26 | UID, DTSTAMP and DTSTART presence and repetition in VEVENT; DTEND and DURATION together; DTEND not later than DTSTART; RRULE with COUNT and UNTIL, with no FREQ, with FREQ out of first position, or with a repeated rule part; unescaped COMMA or SEMICOLON in a TEXT value; an escaped COLON, which the RFC says shall not be escaped; a TZID parameter with no matching VTIMEZONE in the same object; PRODID and VERSION presence and repetition; BEGIN and END structure, including a VEVENT nested in a VEVENT; a line with no COLON; a line whose bytes are not UTF-8 and are not at a fold boundary; a bare LF where the grammar requires CRLF. |
| SHOULD | 1 | A physical line longer than 75 octets, excluding the line break. |
| note | 3 | A physical line whose own bytes do not decode as strict UTF-8 at a fold boundary, which is the signature of a fold placed inside a multi-octet sequence. A once-per-file signature note when every fold point carrying non-ASCII text cuts at a character count that really is the fold width, rather than at an octet count. And a note when DTSTART and DTEND sit in two different named timezones, where ordering them would need a timezone database this page does not ship. |

Only properties whose direct parent is the VEVENT count as the event's. A VALARM inside an event carries its own DURATION, its own REPEAT and, per RFC 9074, its own UID, and none of those is the event's.

Five refusals, each with its own message, none of which dumps a wall of findings: empty input, input past the byte limit, input past the physical-line limit, input with no `BEGIN:VCALENDAR` content line, and bytes that are largely undecodable as UTF-8. A truncated object is checked, with the report led by a line saying the findings may be incomplete.

**Build.** Fill the event form and the page emits a complete VCALENDAR. Output is folded at 75 octets measured over the UTF-8 encoding, never inside a multi-octet sequence, every line terminated CRLF, every TEXT value escaped per section 3.3.11. That is output hygiene, not a fix for a violation: folding is recommended by the RFC, not required by it. The generated bytes are then fed straight back through the validator on the same page, so the verdict you read is computed in front of you rather than promised.

**Run self test.** The button runs 103 assertions and one deliberate failure. 30 of the assertions are positive controls, one per check, each a fixture built to trip exactly that check. Each control asserts the exact set of checks its fixture reports, not merely that the check under test fired, so a detector that fires on everything fails its own control and a fixture that quietly trips a second check fails too. A clean fixture is asserted to produce zero findings of any tier. The rest check everything else the page promises, including the fixtures themselves, conforming shapes that must stay silent, the five input refusals, the folder and the TEXT escaper, builder inputs that must be refused rather than emitted, and legal builder inputs that must still be built. The deliberate failure is the last row, a positive control written to fail on purpose: if it ever stops failing, or does not appear, the self test has stopped running and nothing above it can be trusted. Press the button and the counts in this paragraph are recomputed in your browser.

## Why this exists

The honest claim, and it is narrower than most calendar linters advertise: this reports RFC 5545 MUST violations, plus SHOULD-level findings and interoperability notes, offline, with the normative sentence attached to each one so you can check the tool rather than trust it.

**A file that fails only SHOULD-level checks is still a conforming iCalendar object.** That sentence is why the three counts are reported separately and never summed into one error number. RFC 5545 section 3.1 says lines of text SHOULD NOT be longer than 75 octets, and section 5 item 1 says content lines longer than 75 octets SHOULD be folded. Both are recommendations. A file full of long lines is untidy, not broken, and this page never calls it invalid.

The same care applies to folding. A fold that lands inside a UTF-8 multi-octet sequence is reported as a note, never as a violation, because section 3.1 requires the consumer to unfold correctly and its own Note tells implementations to restore the original sequence. This page does not claim that such a file misbehaves elsewhere, and it does not claim to have found one in the wild. The fixture for that check is hand-built, and the page says so.

It does compare DTEND to DTSTART, and only where that comparison needs nothing but the two values. RFC 5545 section 3.8.2.2 says of DTEND, inside a VEVENT, `its value MUST be later in time than the value of the "DTSTART" property`. The check runs when both values are in UTC, both are floating local time, or both carry the same TZID string, because those are the cases where ordering is a fixed-width string comparison. When the two carry different TZIDs, the page reports that they are not comparable without resolving a timezone, and stops.

It ships no timezone database and never will. A TZID is checked only against VTIMEZONE components inside the same file, and no offset is ever resolved, not from a table and not from the browser. If a browser timezone update could change the verdict on a fixed input, the verdict is not deterministic, and a deterministic verdict is the only thing this page sells. That is also why the ordering check stops at the boundary above rather than guessing across it.

Behaviour was reimplemented from the published specification, no code is reproduced here. The normative sentences shown with each finding are quotations from RFC 5545, "Internet Calendaring and Scheduling Core Object Specification (iCalendar)", September 2009. ## Privacy

Everything runs in your browser. Nothing leaves your machine.

The page makes no network call of any kind. There is no CDN, no framework, no web font, no analytics and no beacon. Uploaded files are read locally with `FileReader` and never transmitted. Because a calendar export is a list of where you were and who you were with, that property is the point, not a footnote: open the page once and you can run it with the network off forever.

Untrusted input is treated as data, never as markup. Every node in the report is built with `createElement` and `textContent`; nothing user-derived ever reaches `innerHTML`. There is no `eval` and no `new Function`. Input size and line count are bounded, so a file past either limit is refused rather than read. Rendering is bounded separately, because a file can sit well inside both limits and still have hundreds of thousands of offending lines: each check renders at most 400 findings and then adds one row saying how many more it found. The verdict counts are taken from the detector, not from the rendered list, so the three headline numbers stay exact while the page stays responsive.

## Run locally

    git clone https://github.com/0xelitesystem/ics-calendar-builder-and-validator.git
    cd ics-calendar-builder-and-validator

Open `index.html` in a browser. It works from `file://` with no server.

If you prefer a server:

    python -m http.server 8000

then open http://localhost:8000/ and press Run self test to confirm the copy you are looking at behaves.

Note that some sandboxed viewers block script-driven downloads. In Build mode, Copy output is the primary path and Download .ics is the convenience.

## Build

No build step. One file, `index.html`, with inline CSS and JavaScript. No dependencies, no package manager, no bundler, nothing to install.
